
**星型模型的“黄金法则”** ：
- **维度表放“描述信息”** ：客户名称、产品名称、日期、分类——这些是“用于筛选和分组的文本”
- **事实表放“可度量的数值”** ：销售额、数量、利润——这些是“用于计算和汇总的数字”


### 1.4 表关系（Relationship）

在Power BI中，表关系决定了不同表之间如何“联动”——你拖拽一个维度到图表中，相关的数值会自动汇总。

**关系类型**：

| 类型 | 含义 | 示例 |
|:-----|:-----|:-----|
| **一对多（1:*）** | 维度表中的一条记录对应事实表中的多条记录 | 一个客户有多个订单 |
| **一对一（1:1）** | 一条记录对应一条记录 | 很少见，通常应合并 |
| **多对多（*:*）** | 多条记录对应多条记录 | 需要特殊处理，尽量避免 |

**关系方向**：

| 方向 | 含义 | 说明 |
|:-----|:-----|:-----|
| **单向** | 筛选方向从一个表流向另一个表 | 最常见：维度→事实 |
| **双向** | 筛选方向在两个表间互相流通 | 谨慎使用，会导致性能下降和歧义 |


### 1.5 计算列 vs 度量值

这是Power BI建模中最容易混淆的概念——也是面试中最高频的问题之一。

**计算列（Calculated Column）** ：

| 属性 | 说明 |
|:-----|:-----|
| **定义** | 在表中新增一列，为每一行计算一个值 |
| **计算时机** | 数据加载时计算一次，存储在模型中 |
| **存储** | 占用内存和存储空间 |
| **使用场景** | 需要对行级数据进行转换（如计算“含税价格 = 单价 × 1.13”） |
| **性能影响** | 增加模型的存储压力和刷新时间 |

**度量值（Measure）** ：

| 属性 | 说明 |
|:-----|:-----|
| **定义** | 在报表交互时动态计算，不存储在表中 |
| **计算时机** | 每次交互时动态计算 |
| **存储** | 不占用存储空间 |
| **使用场景** | 需要动态汇总的计算（如“总销售额”“同比增长率”） |
| **性能影响** | 无存储负担，但复杂度量值可能影响查询速度 |

**核心区别**：

| 维度 | 计算列 | 度量值 |
|:-----|:-------|:-------|
| 计算时机 | 数据加载时 | 查询时（动态）|
| 存储方式 | 存储在模型中 | 不存储 |
| 结果精度 | 行级（每行一个值）| 汇总级（取决于上下文）|
| 占用资源 | 增加存储 | 增加计算 |
| 典型用途 | 行级数据转换 | 动态聚合计算 |

> **经验法则**：
> - 需要对每一行单独计算并存储结果 → 用**计算列**（如“含税价格”“全名拼接”）
> - 需要动态汇总、受筛选器影响 → 用**度量值**（如“总销售额”“平均客单价”）
> - 尽量多用度量值、少用计算列，因为度量值更灵活、更节省存储空间


### 1.6 日期表（Date Table）

在Power BI中，日期表是**几乎所有时间序列分析的前置条件**——没有独立的日期表，就无法做同比、环比、累计等时间智能计算。

**为什么需要独立的日期表？**

| 原因 | 说明 |
|:-----|:-----|
| 事实表中的日期可能不连续 | 没有销售的日子在数据中不存在，但时间计算需要连续的日期 |
| 需要完整的日期属性 | 如年、季度、月、周、工作日、节假日标记 |
| 时间智能函数需要日期表 | DAX的`TOTALYTD`、`SAMEPERIODLASTYEAR`等函数都需要独立的日期表 |

**Power BI中创建日期表的两种方式**：

| 方式 | 说明 | 适用场景 |
|:-----|:-----|:---------|
| **自动创建** | Power BI会自动为日期字段创建隐藏日期表 | 简单分析，快速上手 |
| **手动创建** | 用DAX`CALENDAR()`函数创建完整的日期表 | 需要完整日期属性和时间智能计算 |

**日期表的最低要求**：
- 包含连续的日期（从最早到最晚，每一天都要有）
- 包含日期字段（格式为日期类型）
- 标记为“日期表”


### 1.7 数据模型的性能优化

当数据量大（数百万行）或计算复杂时，数据模型可能变慢。以下是几条核心优化原则。

| 优化原则 | 说明 | 效果 |
|:---------|:-----|:-----|
| **减少列** | 只导入需要的列，删除不需要的列 | 减少内存占用和刷新时间 |
| **减少行** | 在Power Query中提前过滤数据，不要把所有历史数据都导入 | 减少内存占用 |
| **正确设置数据类型** | 文本类型用“文本”，数值类型用“整数/小数”，日期用“日期” | 确保计算正确、节省存储 |
| **避免双向筛选** | 除非必要，使用单向筛选 | 避免查询歧义和性能下降 |
| **用度量值替代计算列** | 能用度量值就不用计算列 | 减少存储负担 |
| **使用聚合表** | 为超大事实表预先创建聚合表（高级用法，需要企业版或Premium容量）| 大幅提升查询速度（适用于亿级数据场景）|


## 二、商业场景还原

> 本节将数据连接与建模还原到真实的商业情境中。


### 场景1：从Excel到Power BI——销售数据建模

**情境**：你有三张Excel表：
- 订单表（订单ID、订单日期、客户ID、产品ID、数量、单价）
- 客户表（客户ID、客户名称、城市、注册日期）
- 产品表（产品ID、产品名称、类别、成本价）

需要将这三张表导入Power BI，建立数据模型，以便分析“各城市各产品的销售额”。

**建模步骤**：

1. **导入数据**：
   - Power BI → 获取数据 → Excel → 选择三张表
   - 或使用Power Query编辑器：将“订单表”中的“订单日期”列类型设为“日期”

2. **建立表关系**：
   - 订单表[客户ID] ← 1:* → 客户表[客户ID]
   - 订单表[产品ID] ← 1:* → 产品表[产品ID]
   - （可选）如果订单表中有“订单日期”列，创建日期表并连接“订单日期”和“日期表[Date]”

3. **设置数据模型**：
   - 确定各表角色：订单表=事实表，客户表/产品表=维度表（如有日期表也属于维度表）
   - 确保所有关系为“一对多”，方向从维度表指向事实表
   - 隐藏不需要的列（如客户表中的内部ID字段，如非必要，可隐藏以避免用户混淆）

4. **创建度量值**：
   - 销售额 = `SUMX(订单表, 订单表[数量] * 订单表[单价])`
   - 订单量 = `COUNTROWS(订单表)`
   - 客单价 = `[销售额] / [订单量]`

5. **验证模型**：
   - 拖拽“客户表[城市]”到图表，拖拽“[销售额]”到值区域——验证数据是否正确


### 场景2：多数据源合并——从数据库+Excel整合数据

**情境**：
- 订单数据在SQL Server数据库中（每天新增数万行）
- 产品分类信息在Excel文件中（由市场部维护，不定期更新）
- 需要将两者整合到一个模型中分析

**建模步骤**：

1. **连接SQL Server**：获取数据 → SQL Server → 选择订单表（使用“导入”模式）
2. **连接Excel文件**：获取数据 → Excel → 选择产品分类表
3. **在Power Query中做数据转换**：
   - 在订单表中筛选“订单状态 = ‘已完成’”
   - 删除不必要的列（如备注、操作日志等）
   - 将“订单日期”列格式化为日期类型
4. **建立表关系**：订单表[产品ID] → 产品分类表[产品ID]
5. **设置增量刷新**（见20-3-4详述）：
   - 将“订单日期”作为增量字段，设置每次只刷新最近N天的数据
   - 避免每次刷新都全量加载数百万行历史订单


### 场景3：星型模型设计——零售业分析

**情境**：零售企业有销售明细表，需要按“时间、门店、品类、促销活动”等多个维度分析销售额。

**建议模型结构**：

| 表名 | 角色 | 主要字段 | 数据量级 |
|:-----|:-----|:---------|:---------|
| `销售事实表` | 事实表 | 日期、门店ID、品类ID、促销ID、销售额、销售量 | 大（百万级）|
| `日期维度表` | 维度表 | 日期、年、季、月、周、是否周末 | 小（365行/年）|
| `门店维度表` | 维度表 | 门店ID、门店名称、城市、区域、面积 | 小（数百行）|
| `品类维度表` | 维度表 | 品类ID、品类名称、大类、毛利率 | 小（数十行）|
| `促销维度表` | 维度表 | 促销ID、促销名称、类型、折扣率、起止日期 | 小（数百行）|

**关系设置**：
- 所有维度表 → 销售事实表（一对多，单向筛选）
- 日期维度表是“日期表”，标记为日期表

**关键度量值**：
- `总销售额 = SUM(销售事实表[销售额])`
- `同比 = [总销售额] - CALCULATE([总销售额], SAMEPERIODLASTYEAR(日期表[日期]))`
- `促销占比 = [促销销售额] / [总销售额]`


## 三、常见错误与陷阱

| 错误 | 后果 | 正确做法 |
|:-----|:-----|:---------|
| 直接将所有表导入，不建立关系 | 各表独立，无法交叉分析 | 建立表关系，设计星型模型 |
| 分不清事实表和维度表 | 建模混乱，计算错误 | 事实表放数值，维度表放描述 |
| 过度使用计算列 | 模型变大、刷新变慢 | 能用度量值就不用计算列 |
| 忘记创建日期表 | 时间智能计算无法使用 | 创建独立的日期表，标记为日期表 |
| 建立了双向筛选关系 | 性能下降、计算结果可能出错 | 默认用单向筛选（从维度到事实）|
| 在Power Query中做了大量数据转换后才建立关系 | 转换复杂且维护困难 | 先建立表关系，再在关系中做转换（或使用Power Query的“添加查询”步骤模块化处理）|
