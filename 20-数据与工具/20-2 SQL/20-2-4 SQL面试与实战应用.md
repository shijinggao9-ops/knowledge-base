## 一、核心概念词典

### 1.1 窗口函数概述

**什么是窗口函数？**

窗口函数在不改变查询结果行数的情况下，对每一行计算基于“窗口”（一组相关行）的聚合值或排名值。与`GROUP BY`不同，窗口函数不会把多行合并为一行——它保留原始行，并在每一行旁边附加窗口计算结果。

**窗口函数 vs GROUP BY 的核心区别**：

| 维度 | GROUP BY | 窗口函数 |
|:-----|:----------|:---------|
| 结果行数 | 减少（每组一行）| 不变（保留原始行数）|
| 用途 | 分组汇总，获取“整体摘要” | 在保留明细的同时，计算“行级上下文” |
| 典型场景 | “每个城市的总销售额” | “每个订单的金额与其城市平均值的差额” |

**窗口函数的核心语法**：

```sql
SELECT
  列名,
  窗口函数() OVER (
    PARTITION BY 分组列   -- 可选：定义窗口的分组
    ORDER BY 排序列       -- 可选：定义窗口内的排序
    ROWS/RANGE BETWEEN ... -- 可选：定义窗口的边界
  ) AS 别名
FROM 表名;
```

**窗口函数的执行顺序**：

`FROM → WHERE → GROUP BY → HAVING → SELECT → 窗口函数 → ORDER BY → LIMIT

窗口函数在`SELECT`阶段执行，其结果是作为查询结果的一部分被附加到每一行上。理解这个顺序可以帮你避免在`WHERE`中误用窗口函数（窗口函数的结果不能直接用于`WHERE`过滤，除非通过子查询）。

**窗口函数的三大组成部分**：

|部分|关键字|作用|是否必须|
|---|---|---|---|
|**分区**（Partition）|`PARTITION BY`|将数据分成独立的“窗口”（类似于`GROUP BY`）|可选|
|**排序**（Order）|`ORDER BY`|定义窗口内的排序（对排名类和前后行访问类函数是必须的）|视函数而定|
|**框架**（Frame）|`ROWS/RANGE BETWEEN`|定义窗口的边界范围（用于累计类窗口函数）|可选|

### 1.2 排名类窗口函数

`RANK()`、`DENSE_RANK()`和`ROW_NUMBER()`用于对窗口内的行进行排序编号。

|函数|行为|示例结果（分数：95, 95, 90）|
|---|---|---|
|`ROW_NUMBER()`|按顺序编号，**并列时随机分配不同序号**|1, 2, 3|
|`RANK()`|排名，**并列时跳过后续名次**|1, 1, 3|
|`DENSE_RANK()`|排名，**并列时不跳过后续名次**|1, 1, 2|

**示例**：按销售额对销售员排名

```sql

SELECT
  salesperson,
  SUM(amount) AS total_sales,
  ROW_NUMBER() OVER (ORDER BY SUM(amount) DESC) AS row_num,
  RANK() OVER (ORDER BY SUM(amount) DESC) AS rank_num,
  DENSE_RANK() OVER (ORDER BY SUM(amount) DESC) AS dense_rank_num
FROM orders
GROUP BY salesperson;
```

**使用场景速查**：

|需求|使用函数|
|---|---|
|“给每行加一个行号”|`ROW_NUMBER()`|
|“业务排名（允许并列、跳号）”|`RANK()`|
|“业务排名（允许并列、不跳号）”|`DENSE_RANK()`|
|“取每个分组的前N条记录”|`ROW_NUMBER()` + 子查询过滤|

#### 分组排名：PARTITION BY

按部门内排名（每个部门内按薪资排序）：

```sql

SELECT
  department,
  name,
  salary,
  RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS rank_in_dept
FROM employees;
```

### 1.3 前后行访问函数：LAG 与 LEAD

`LAG()`和`LEAD()`用于访问当前行**之前或之后**的行数据——是计算同比、环比的核心工具。

|函数|语法|用途|示例|
|---|---|---|---|
|`LAG`|`LAG(列名, 偏移量, 默认值)`|访问当前行之前的第N行|上个月的销售额|
|`LEAD`|`LEAD(列名, 偏移量, 默认值)`|访问当前行之后的第N行|下个月的销售额|

**示例**：计算月度销售额的环比增长率

```sql

WITH monthly_sales AS (
  SELECT
    DATE_FORMAT(order_date, '%Y-%m') AS month,
    SUM(amount) AS sales
  FROM orders
  GROUP BY DATE_FORMAT(order_date, '%Y-%m')
)
SELECT
  month,
  sales,
  LAG(sales, 1) OVER (ORDER BY month) AS prev_month_sales,
  (sales - LAG(sales, 1) OVER (ORDER BY month)) / LAG(sales, 1) OVER (ORDER BY month) * 100 AS growth_rate_pct
FROM monthly_sales
ORDER BY month;
```

**执行逻辑**：

- `LAG(sales, 1)`：取当前行的前一行（上个月）的`sales`值
    
- 第1行（最早月份）的前一行不存在，返回`NULL`
    
- 通过`(本月-上月)/上月`计算增长率
    

### 1.4 累计与移动窗口函数

#### 累计求和

```sql

SELECT
  order_date,
  daily_sales,
  SUM(daily_sales) OVER (ORDER BY order_date) AS cumulative_sales
FROM daily_sales_data
ORDER BY order_date;
```

#### 移动平均

```sql

SELECT
  order_date,
  daily_sales,
  AVG(daily_sales) OVER (
    ORDER BY order_date
    ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ) AS ma_7d
FROM daily_sales_data
ORDER BY order_date;
```

`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW`表示“当前行及前6行”，即7日移动平均。

#### 占比计算

```sql

SELECT
  product,
  sales,
  sales * 1.0 / SUM(sales) OVER () AS sales_pct
FROM product_sales;
```

`SUM(sales) OVER ()`计算所有行的总销售额（无`PARTITION BY`，整个结果集为一个窗口）。

### 1.5 面试高频题

数据分析/商业分析岗位SQL笔试中最高频的题型。

#### 题型一：连续登录问题

**题目**：查询“连续登录至少3天的用户”。

```sql

WITH user_login_dates AS (
  SELECT
    user_id,
    login_date,
    -- 为每个用户按日期排序并编号
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn
  FROM user_logins
  -- 如果用户一天可能多次登录，需要先去重
  GROUP BY user_id, login_date
),
groups AS (
  SELECT
    user_id,
    login_date,
    -- 用登录日期减去行号，如果日期连续，差值相同
    DATE_SUB(login_date, INTERVAL rn DAY) AS grp
  FROM user_login_dates
)
SELECT
  user_id,
  MIN(login_date) AS start_date,
  MAX(login_date) AS end_date,
  COUNT(*) AS consecutive_days
FROM groups
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;
```

**核心逻辑**：连续日期的`日期 - 行号`是常量。

|日期|行号|日期 - 行号|
|---|---|---|
|2026-01-01|1|2025-12-31|
|2026-01-02|2|2025-12-31|
|2026-01-03|3|2025-12-31|
|2026-01-05|4|2026-01-01|

#### 题型二：分组排名与Top N

**题目**：查询“每个品类销量最高的前3个产品”。

```sql

WITH product_ranking AS (
  SELECT
    p.category,
    p.product_name,
    SUM(oi.quantity) AS total_quantity,
    ROW_NUMBER() OVER (PARTITION BY p.category ORDER BY SUM(oi.quantity) DESC) AS rn
  FROM products p
  INNER JOIN order_items oi ON p.product_id = oi.product_id
  GROUP BY p.category, p.product_id, p.product_name
)
SELECT
  category,
  product_name,
  total_quantity,
  rn AS rank_in_category
FROM product_ranking
WHERE rn <= 3
ORDER BY category, rn;
```

#### 题型三：同比/环比计算

**题目**：计算“2026年各月份销售额的同比（对比2025年同月）”。

```sql

WITH monthly_sales AS (
  SELECT
    YEAR(order_date) AS year,
    MONTH(order_date) AS month,
    SUM(amount) AS sales
  FROM orders
  WHERE order_date >= '2025-01-01'
  GROUP BY YEAR(order_date), MONTH(order_date)
)
SELECT
  year,
  month,
  sales,
  LAG(sales, 12) OVER (ORDER BY year, month) AS sales_prev_year,
  (sales - LAG(sales, 12) OVER (ORDER BY year, month)) / LAG(sales, 12) OVER (ORDER BY year, month) * 100 AS yoy_growth_pct
FROM monthly_sales
WHERE year = 2026
ORDER BY month;
```

**关键点**：`LAG(sales, 12)`取12个月前的值——即去年同月。

#### 题型四：去重与保留最新记录

**题目**：一张`user_activities`表有重复记录（同一用户+同一日期有多条记录），要求保留每个用户每天最新的记录（按`activity_time`最新）。

```sql

WITH ranked AS (
  SELECT
    *,
    ROW_NUMBER() OVER (PARTITION BY user_id, DATE(activity_time) ORDER BY activity_time DESC) AS rn
  FROM user_activities
)
SELECT *
FROM ranked
WHERE rn = 1;
```

#### 题型五：留存率计算

**题目**：计算2026年1月注册用户的“次日留存率”“7日留存率”“30日留存率”。

```sql

WITH signup_cohort AS (
  SELECT
    user_id,
    MIN(signup_date) AS signup_date
  FROM users
  WHERE signup_date BETWEEN '2026-01-01' AND '2026-01-31'
  GROUP BY user_id
),
user_activity AS (
  SELECT
    user_id,
    DATE(activity_time) AS active_date
  FROM user_actions
  GROUP BY user_id, DATE(activity_time)
),
cohort_retention AS (
  SELECT
    s.user_id,
    s.signup_date,
    DATEDIFF(a.active_date, s.signup_date) AS days_since_signup
  FROM signup_cohort s
  LEFT JOIN user_activity a ON s.user_id = a.user_id
)
SELECT
  signup_date,
  COUNT(DISTINCT user_id) AS signups,
  COUNT(DISTINCT CASE WHEN days_since_signup = 1 THEN user_id END) / COUNT(DISTINCT user_id) AS retention_d1,
  COUNT(DISTINCT CASE WHEN days_since_signup = 7 THEN user_id END) / COUNT(DISTINCT user_id) AS retention_d7,
  COUNT(DISTINCT CASE WHEN days_since_signup = 30 THEN user_id END) / COUNT(DISTINCT user_id) AS retention_d30
FROM cohort_retention
GROUP BY signup_date
ORDER BY signup_date;
```

### 1.6 查询性能优化

当数据量增大时，SQL查询可能变得很慢。以下是最核心的优化原则。

#### 优化原则一：避免 SELECT *

```sql

-- ❌ 慢：返回所有列，浪费网络带宽和内存
SELECT * FROM orders WHERE order_date >= '2026-01-01';
-- ✅ 快：只返回需要的列
SELECT order_id, customer_id, amount FROM orders WHERE order_date >= '2026-01-01';
```
#### 优化原则二：避免在 WHERE 中对列使用函数

```sql

-- ❌ 慢：对每一行都要执行MONTH()函数，无法使用索引
SELECT * FROM orders WHERE MONTH(order_date) = 8;
-- ✅ 快：使用范围条件，可以利用索引
SELECT * FROM orders WHERE order_date BETWEEN '2026-08-01' AND '2026-08-31';
```

#### 优化原则三：使用 EXISTS 替代 IN（子查询返回大量数据时）

```sql

-- ❌ 子查询返回大量数据时可能较慢（IN需要完整执行子查询并生成结果集）
SELECT * FROM customers WHERE customer_id IN (SELECT customer_id FROM orders WHERE amount > 1000);
-- ✅ 推荐：用EXISTS（存在匹配即停止，不需要生成完整结果集）
SELECT * FROM customers c WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.amount > 1000
);
```

#### 优化原则四：JOIN 时确保关联列有索引

```sql

-- 在连接条件列上创建索引（在连接操作频繁的列上特别重要）
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_customers_id ON customers(customer_id);
```

#### 优化原则五：用 UNION ALL 替代 UNION（明确不需要去重时）

```sql

-- ✅ UNION ALL 更快（不去重，不排序）
SELECT name FROM sales_2025
UNION ALL
SELECT name FROM sales_2026;
-- ❌ UNION 更慢（需要去重和排序）
SELECT name FROM sales_2025
UNION
SELECT name FROM sales_2026;
```

#### 优化原则六：使用 EXPLAIN 分析查询计划

```sql

EXPLAIN SELECT ...;  -- 查看数据库如何执行该查询

- `EXPLAIN`可以看到是否使用了索引、扫描了多少行、表连接顺序等
    
- 关注`type`列：`ALL`（全表扫描）→ 需要优化；`index`（索引扫描）→ 较好；`ref`/`eq_ref`（精准索引查找）→ 最优
    
```

## 二、商业场景还原

### 场景1：销售排名与奖励计算

**情境**：公司按季度销售额对销售员排名，前3名发放奖金。

```sql

WITH sales_ranking AS (
  SELECT
    salesperson,
    SUM(amount) AS total_sales,
    RANK() OVER (ORDER BY SUM(amount) DESC) AS sales_rank
  FROM orders
  WHERE order_date BETWEEN '2026-01-01' AND '2026-03-31'
  GROUP BY salesperson
)
SELECT
  salesperson,
  total_sales,
  sales_rank,
  CASE
    WHEN sales_rank = 1 THEN '奖金5000'
    WHEN sales_rank = 2 THEN '奖金3000'
    WHEN sales_rank = 3 THEN '奖金2000'
    ELSE '无奖金'
  END AS bonus
FROM sales_ranking
ORDER BY sales_rank;
```

### 场景2：用户行为序列分析

**情境**：分析用户在使用产品时的路径——用户注册后，最常执行的“第3个动作”是什么？

```sql

WITH user_actions_ranked AS (
  SELECT
    user_id,
    action_name,
    action_time,
    ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY action_time) AS action_seq
  FROM user_actions
)
SELECT
  action_name,
  COUNT(*) AS user_count
FROM user_actions_ranked
WHERE action_seq = 3
GROUP BY action_name
ORDER BY user_count DESC;
```

### 场景3：库存预警——累计采购量 vs 安全库存

```sql

WITH cumulative_purchases AS (
  SELECT
    product_id,
    purchase_date,
    quantity,
    SUM(quantity) OVER (PARTITION BY product_id ORDER BY purchase_date) AS cum_quantity
  FROM purchases
)
SELECT
  product_id,
  purchase_date,
  quantity,
  cum_quantity,
  CASE
    WHEN cum_quantity >= 1000 THEN '库存充足'
    WHEN cum_quantity >= 500 THEN '补货提醒'
    ELSE '紧急补货'
  END AS stock_status
FROM cumulative_purchases;
```

## 三、面试/实战中怎么用

### 3.1 面试中的SQL答题策略

|步骤|操作|说明|
|---|---|---|
|**1. 读懂题意**|确认3件事：要查询什么、数据来自哪些表、筛选条件是什么|不要急于写代码，先理解业务逻辑|
|**2. 确定查询结构**|需要JOIN吗？需要GROUP BY吗？需要子查询/窗口函数吗？|从“要什么结果”倒推“用什么方法”|
|**3. 分步构建**|先写FROM+WHERE，再加JOIN，再加GROUP BY，最后加排序/限制|逐步验证，避免一次性写完再调试|
|**4. 考虑边界**|有没有NULL？有没有重复？有没有一对多导致数量膨胀？|面试官会追问边界情况|
|**5. 优化写法**|能用窗口函数就不用手动子查询；能用EXISTS就不用IN大表|展示你的SQL“熟练度”|

### 3.2 面试官追问的“边界情况”

|追问|正确回应|
|---|---|
|“如果用户一天多次登录，你的连续登录查询会错吗？”|“需要先用`GROUP BY user_id, login_date`去重，再做连续登录判断。”|
|“如果某个月没有销售数据，你的同比计算会怎样？”|“用`COALESCE`或`IFNULL`处理NULL值，或默认填充0。”|
|“如果客户表有100万行，你的查询会慢吗？”|“我会在`customer_id`和`order_date`上建索引，避免全表扫描。”|

### 3.3 面试中展示“SQL思维”的技巧

|技巧|示例话术|
|---|---|
|先讲思路再写代码|“我先用WITH子句生成月度汇总，再用LAG计算环比，最后用CASE标记涨跌。”|
|主动提及性能|“这个查询在数据量大时，建议在order_date上建索引。”|
|主动提及边界|“如果订单表中有NULL值，我会先过滤掉。”|
|展示工具选型能力|“如果数据量超过千万级，我会考虑用窗口函数替代自连接，性能更好。”|

## 四、常见误区

|误区|真相|
|---|---|
|“窗口函数可以在WHERE中使用”|❌ 窗口函数在`SELECT`阶段执行，在`WHERE`之后。如果要基于窗口函数过滤，需用子查询或CTE|
|“`ROW_NUMBER()`和`RANK()`没区别”|❌ 在有并列值时，`ROW_NUMBER()`给不同序号（1,2,3），`RANK()`跳号（1,1,3），`DENSE_RANK()`不跳号（1,1,2）|
|“`LAG()`只能取上一行，不能取指定行”|❌ `LAG(列, 偏移量)`可以取任意偏移量的行——`LAG(sales, 12)`取12个月前|
|“`UNION`和`UNION ALL`性能一样”|❌ `UNION`需要去重，会进行排序和去重操作，性能开销远大于`UNION ALL`。除非确实需要去重，否则用`UNION ALL`|
|“索引越多查询越快”|❌ 索引能加速查询，但会拖慢写入（`INSERT`/`UPDATE`/`DELETE`）。需根据查询频率和写入频率平衡|
|“`EXPLAIN`的结果太复杂，不用看”|❌ `EXPLAIN`是性能优化的核心工具——至少要看`type`（ALL=全表扫描，需优化）和`rows`（扫描行数）|
