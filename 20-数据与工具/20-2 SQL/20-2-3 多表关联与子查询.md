# 20-2-3 多表关联与子查询（JOIN、子查询、UNION）

**定位**：真实的企业数据从来不会存放在一张“万能的表”里——订单、客户、产品、库存、支付等信息通常分散在十几张甚至上百张表中。学会从单张表取数只是SQL的“入门”，真正的核心能力是把这些分散的表按照逻辑关系“拼”在一起。`JOIN`让你把多张表按共同字段合并为一张宽表，子查询让你在一个查询中嵌套另一个查询（在表中查询表），`UNION`让你把多个查询的结果上下堆叠。理解多表关联，是SQL能力从“初学者”到“独立完成复杂取数任务”的关键一跃。

**适用场景**：将订单表与客户表关联获取客户信息、将销售表与产品表关联获取产品分类、将员工表与部门表关联获取组织架构、面试中的多表关联SQL题、数据仓库中的多维度分析。


## 一、核心概念词典

### 1.1 为什么需要多张表？——数据库的“规范化”

在企业数据库中，数据不是放在一张大表里的，而是分散在多张“规范化”的表中。理解这一点，是理解JOIN的前提。

| 设计原则 | 含义 | 示例 |
|:---------|:-----|:-----|
| **消除冗余** | 同一信息只存一次，避免重复 | 客户信息存客户表，订单表只存customer_id，不存客户姓名 |
| **减少维护成本** | 信息变更只需改一处 | 客户改地址，只更新客户表，所有订单自动关联新地址 |
| **清晰的结构** | 不同业务实体分开存储 | 订单表、客户表、产品表、支付表……各司其职 |

**一个规范化数据库的典型结构**：
客户表（customers） 订单表（orders）  
┌─────────────┐ ┌─────────────┐  
│ customer_id │ ←───外键关联─── │ customer_id │  
│ name │ │ order_id │  
│ email │ │ order_date │  
│ city │ │ amount │  
└─────────────┘ └─────────────┘  
↑ ↑  
│ │  
产品表（products） 订单明细表（order_items）  
┌─────────────┐ ┌─────────────┐  
│ product_id │ ←───外键关联─── │ product_id │  
│ product_name│ │ order_id │  
│ category │ │ quantity │  
│ price │ │ price │  
└─────────────┘ └─────────────┘

### 1.2 主键与外键
理解JOIN之前，必须先理解“表与表之间是如何连接的”——这就是主键和外键的作用。

| 概念 | 定义 | 特征 | 示例 |
|:-----|:-----|:-----|:-----|
| **主键**（Primary Key）| 唯一标识表中每一行的列 | 唯一、非空、不变 | `customer_id`、`order_id` |
| **外键**（Foreign Key）| 引用另一张表主键的列 | 可重复、可为空 | 订单表中的`customer_id`引用客户表的`customer_id` |
**表关系类型**：

| 关系类型 | 定义 | 业务示例 |
|:---------|:-----|:---------|
| **一对一**（1:1）| A表中的一条记录对应B表中的一条记录 | 用户表↔用户详情表（很少用，通常合并为一张表）|
| **一对多**（1:N）| A表中的一条记录对应B表中的多条记录 | 客户表↔订单表（一个客户有多个订单）|
| **多对多**（M:N）| A表中的多条记录对应B表中的多条记录 | 学生表↔课程表（一个学生选多门课，一门课有多个学生），需要中间表 |
### 1.3 JOIN 系列总览
`JOIN`用于将两张或多张表按一定条件合并为一张结果表。

| JOIN类型 | 关键字 | 返回结果 | 使用频率 |
|:---------|:-------|:---------|:--------:|
| **内连接** | `INNER JOIN` | 只返回匹配的记录 | ⭐⭐⭐⭐⭐ |
| **左连接** | `LEFT JOIN` | 返回左表所有记录，右表匹配不上则为NULL | ⭐⭐⭐⭐⭐ |
| **右连接** | `RIGHT JOIN` | 返回右表所有记录，左表匹配不上则为NULL | ⭐⭐ |
| **全连接** | `FULL OUTER JOIN` | 返回所有记录，匹配不上则为NULL | ⭐ |
| **交叉连接** | `CROSS JOIN` | 两表的笛卡尔积（所有组合）| ⭐ |
> MySQL不直接支持`FULL OUTER JOIN`，但可以用`UNION`组合`LEFT JOIN`和`RIGHT JOIN`实现。
### 1.4 INNER JOIN（内连接）
`INNER JOIN`返回两张表中**都匹配**的记录——这是最常用的JOIN类型。
**语法**：
```sql
SELECT 列名
FROM 表A
INNER JOIN 表B ON 表A.外键 = 表B.主键;
```
**示例**：查询所有订单的客户姓名

```sql

SELECT
  o.order_id,
  o.order_date,
  o.amount,
  c.name AS customer_name,
  c.city
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id;
```

**执行逻辑**：

1. 从`orders`表取一条记录
    
2. 用`o.customer_id`去`customers`表中查找`c.customer_id`相同的记录
    
3. 如果找到，则合并两表的列，输出一条结果
    
4. 如果找不到，则跳过该条订单
    

**输出**：

|order_id|order_date|amount|customer_name|city|
|---|---|---|---|---|
|1001|2026-01-15|2,500|张三|北京|
|1002|2026-01-16|1,800|李四|上海|
|1003|2026-01-16|5,000|张三|北京|

> 如果某条订单的`customer_id`在`customers`表中不存在（数据异常），这条订单不会出现在`INNER JOIN`的结果中。

#### 三张表JOIN

```sql

SELECT
  o.order_id,
  c.name AS customer_name,
  p.product_name,
  oi.quantity,
  oi.price
FROM orders o
INNER JOIN customers c ON o.customer_id = c.customer_id
INNER JOIN order_items oi ON o.order_id = oi.order_id
INNER JOIN products p ON oi.product_id = p.product_id;
```

**关键点**：

- `FROM`之后可以连续接多个`JOIN`
    
- 每个`JOIN`独立指定连接条件
    
- 连接顺序会影响查询性能（通常把大表放在前面，但优化器会自动调整）
    

### 1.5 LEFT JOIN / RIGHT JOIN（外连接）

#### LEFT JOIN

`LEFT JOIN`返回**左表所有记录**，即使右表中没有匹配——右表不匹配的列显示为`NULL`。

**语法**：

```sql

SELECT 列名
FROM 表A
LEFT JOIN 表B ON 表A.外键 = 表B.主键;
```

**示例**：查询所有客户及其订单信息（即使没有下过单的客户也要显示）

```sql

SELECT
  c.customer_id,
  c.name,
  c.city,
  o.order_id,
  o.order_date,
  o.amount
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;
```

**输出**：

|customer_id|name|city|order_id|order_date|amount|
|---|---|---|---|---|---|
|1|张三|北京|1001|2026-01-15|2,500|
|1|张三|北京|1003|2026-01-16|5,000|
|2|李四|上海|1002|2026-01-16|1,800|
|3|王五|深圳|NULL|NULL|NULL|

> 王五在`customers`表中有记录，但没有下过任何订单——`LEFT JOIN`依然返回王五，订单信息为`NULL`。

**`INNER JOIN` vs `LEFT JOIN`的对比**：

|场景|INNER JOIN|LEFT JOIN|
|---|---|---|
|客户张三（有订单）|✅ 返回|✅ 返回|
|客户王五（无订单）|❌ 不返回|✅ 返回（订单字段为NULL）|

#### RIGHT JOIN

`RIGHT JOIN`与`LEFT JOIN`相反——返回右表所有记录，左表匹配不上则为`NULL`。在实战中，`RIGHT JOIN`很少使用——只需调整表的顺序，用`LEFT JOIN`即可实现同样功能。

```sql

-- 以下两条语句效果完全相同
SELECT * FROM orders o RIGHT JOIN customers c ON o.customer_id = c.customer_id;
SELECT * FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id;
```

### 1.6 自连接（Self Join）

**定义**：一张表**自己连接自己**——当表中有“层级关系”（如员工-经理、商品-分类）时使用。

**示例**：查询员工及其对应的经理姓名

```sql

-- 员工表：emp_id, name, manager_id（指向emp_id）
SELECT
  e.name AS employee_name,
  m.name AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;
```

**关键点**：

- 必须给同一张表起两个**不同的别名**（如`e`和`m`）
    
- `LEFT JOIN`确保没有经理的员工（如CEO）也显示出来
    

### 1.7 子查询

子查询是在一个查询中**嵌套另一个查询**——即“查询中的查询”。它是SQL中最灵活、最强大的功能之一。

**子查询的三种位置**：

|位置|用途|返回值类型|
|---|---|---|
|`WHERE`子句中|用于过滤条件|单个值、一列值、或一张表|
|`FROM`子句中|作为派生表（临时表）|一张表|
|`SELECT`子句中|作为标量值|单个值|

#### WHERE子句中的子查询

**示例1：查询“下单金额超过平均订单金额”的订单**

```sql

SELECT order_id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

子查询先计算`AVG(amount)`（假设为3,500），然后外部查询筛选出`amount > 3,500`的记录.

**示例2：查询“下过单的客户”的信息**

sql

SELECT *
FROM customers
WHERE customer_id IN (
  SELECT DISTINCT customer_id
  FROM orders
);

子查询返回所有下过单的`customer_id`列表，外部查询返回这些客户的完整信息。

**示例3：查询“没有下过单的客户”**

sql

SELECT *
FROM customers
WHERE customer_id NOT IN (
  SELECT DISTINCT customer_id
  FROM orders
);

> **注意**：如果子查询结果中包含`NULL`，`NOT IN`会导致整个查询不返回任何结果（因为`NOT IN (1, 2, NULL)`永远为`FALSE`）。应对方法：在子查询中过滤掉NULL（`WHERE customer_id IS NOT NULL`）或用`NOT EXISTS`替代。

**示例4：查询“在2026年下单超过5笔的客户”**

sql

SELECT *
FROM customers c
WHERE (
  SELECT COUNT(*)
  FROM orders o
  WHERE o.customer_id = c.customer_id
    AND o.order_date >= '2026-01-01'
) >= 5;

这种子查询是**关联子查询**——内部查询引用了外部查询的`c.customer_id`，逐行执行。

#### FROM子句中的子查询（派生表）

当子查询作为`FROM`中的数据源时，它创建了一个**临时的虚拟表**，外部查询可以像操作普通表一样操作它。

sql

SELECT
  city,
  order_count,
  total_sales
FROM (
  SELECT
    city,
    COUNT(*) AS order_count,
    SUM(amount) AS total_sales
  FROM orders
  GROUP BY city
) AS city_stats  -- 必须起别名
WHERE order_count >= 100
ORDER BY total_sales DESC;

#### SELECT子句中的子查询（标量子查询）

子查询返回**单个值**，作为`SELECT`中的一列。

sql

SELECT
  order_id,
  amount,
  (SELECT AVG(amount) FROM orders) AS avg_amount,
  amount - (SELECT AVG(amount) FROM orders) AS diff_from_avg
FROM orders;

### 1.8 EXISTS 与 NOT EXISTS

`EXISTS`和`NOT EXISTS`是子查询的特殊形式，用于检查子查询是否返回了任何记录——它们只关心“是否有”，而不关心“有什么”。

**语法**：

sql

WHERE EXISTS (子查询)
WHERE NOT EXISTS (子查询)

**示例1：查询“下过单的客户”**

sql

SELECT *
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

**示例2：查询“没有下过单的客户”（推荐用NOT EXISTS替代NOT IN）**

sql

SELECT *
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

**`EXISTS` vs `IN`的对比**：

|维度|`IN`|`EXISTS`|
|---|---|---|
|执行方式|先执行子查询，生成结果集，再进行匹配|逐行执行外部查询，对每行执行子查询（存在匹配即停止）|
|NULL处理|子查询中的NULL值会导致`NOT IN`返回空结果集|不受NULL影响（不会因为NULL导致全表结果为空）|
|性能（数据量大时）|子查询结果集较小时较快|子查询结果集较大时较快（尤其是`NOT EXISTS`）|
|子查询返回值|返回一列值（或多个值，取决于具体写法）|只返回“是否存在”，不关心值|
|适用场景|子查询结果集较小时|子查询结果集较大时|

> **经验法则**：当子查询返回大量数据时，用`EXISTS`性能更好；当子查询返回少量数据时，`IN`更清晰易读。

### 1.9 UNION 与 UNION ALL

`UNION`和`UNION ALL`用于**垂直合并**多个查询的结果——即把两个查询的结果“堆叠”在一起。

**UNION vs UNION ALL**：

|操作|行为|适用场景|
|---|---|---|
|`UNION`|合并结果并**去重**|需要唯一结果时|
|`UNION ALL`|合并结果**不去重**|不需要去重时（性能更好）|

**语法**：

sql

SELECT 列1, 列2 FROM 表A
UNION [ALL]
SELECT 列1, 列2 FROM 表B;

**使用条件**：

- 两个查询的**列数必须相同**
    
- 对应的列**数据类型必须兼容**
    

**示例**：合并2025年和2026年的活跃客户

sql

SELECT customer_id FROM orders WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
UNION
SELECT customer_id FROM orders WHERE order_date BETWEEN '2026-01-01' AND '2026-12-31';

**UNION ALL示例**：合并两个部门的员工名单（需要保留重复记录）

sql

SELECT name, department FROM employees WHERE department = '销售部'
UNION ALL
SELECT name, department FROM employees WHERE department = '市场部';

### 1.10 查询执行顺序（完整版）

理解完整的逻辑执行顺序，是写出正确SQL的关键。

text

1. FROM        → 确定数据来源（包括JOIN）
2. WHERE       → 行级过滤
3. GROUP BY    → 分组
4. HAVING      → 分组后过滤
5. SELECT      → 选择列、计算表达式、分配别名
6. ORDER BY    → 排序
7. LIMIT       → 限制返回行数

**这个顺序解释了为什么**：

- `WHERE`中不能使用`SELECT`中定义的别名（别名在`SELECT`阶段才产生）
    
- `ORDER BY`中可以使用别名（`ORDER BY`在`SELECT`之后执行）
    
- `HAVING`中可以使用聚合函数（`HAVING`在`GROUP BY`之后执行）
    

## 二、商业场景还原

> 本节将多表关联与子查询还原到真实的商业情境中。

### 场景1：客户价值分析（三张表JOIN）

**情境**：需要生成一份客户价值分析报表，包含：客户姓名、城市、总订单数、总消费金额、最后一次下单时间、最常购买的产品类别。

sql

SELECT
  c.name,
  c.city,
  COUNT(DISTINCT o.order_id) AS order_count,
  SUM(o.amount) AS total_spent,
  MAX(o.order_date) AS last_order_date,
  (
    SELECT p.category
    FROM order_items oi
    INNER JOIN products p ON oi.product_id = p.product_id
    WHERE oi.order_id IN (
      SELECT order_id FROM orders WHERE customer_id = c.customer_id
    )
    GROUP BY p.category
    ORDER BY SUM(oi.quantity) DESC
    LIMIT 1
  ) AS most_bought_category
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name, c.city
ORDER BY total_spent DESC;

### 场景2：找出“从未下单”的客户（NOT EXISTS）

**情境**：市场部想对从未下过单的客户发送激活邮件。

sql

SELECT
  customer_id,
  name,
  email,
  signup_date
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

### 场景3：各品类销售排名（JOIN + 子查询）

**情境**：需要找出每个品类中销售额最高的产品（“品类销冠”）。

sql

SELECT
  p.category,
  p.product_name,
  SUM(oi.quantity * oi.price) AS total_sales
FROM products p
INNER JOIN order_items oi ON p.product_id = oi.product_id
GROUP BY p.category, p.product_name
HAVING SUM(oi.quantity * oi.price) = (
  SELECT MAX(category_sales)
  FROM (
    SELECT
      p2.category,
      p2.product_name,
      SUM(oi2.quantity * oi2.price) AS category_sales
    FROM products p2
    INNER JOIN order_items oi2 ON p2.product_id = oi2.product_id
    WHERE p2.category = p.category  -- 关联子查询，限定同一品类
    GROUP BY p2.category, p2.product_name
  ) AS t
);

### 场景4：数据一致性检查（LEFT JOIN + IS NULL）

**情境**：检查是否有“孤儿订单”——订单表中的`customer_id`在客户表中不存在。

sql

SELECT
  o.order_id,
  o.customer_id,
  o.order_date
FROM orders o
LEFT JOIN customers c ON o.customer_id = c.customer_id
WHERE c.customer_id IS NULL;

## 三、面试/实战中怎么用

### 3.1 面试高频题

**题目1：“查询每个客户的姓名、订单数、总消费金额”**

sql

SELECT
  c.name,
  COUNT(o.order_id) AS order_count,
  COALESCE(SUM(o.amount), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY total_spent DESC;

> `COALESCE(SUM(o.amount), 0)`确保没有订单的客户显示为0而非NULL。

**题目2：“查询下单次数超过3次的客户”**

sql

SELECT
  c.customer_id,
  c.name,
  COUNT(o.order_id) AS order_count
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
HAVING COUNT(o.order_id) > 3;

**题目3：“查询2026年平均客单价高于整体平均客单价的客户”**

sql

SELECT
  c.customer_id,
  c.name,
  AVG(o.amount) AS avg_order_value
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_date BETWEEN '2026-01-01' AND '2026-12-31'
GROUP BY c.customer_id, c.name
HAVING AVG(o.amount) > (
  SELECT AVG(amount)
  FROM orders
  WHERE order_date BETWEEN '2026-01-01' AND '2026-12-31'
);

**题目4：“查询所有订单金额排名前3的产品”**

sql

SELECT
  p.product_name,
  SUM(oi.quantity * oi.price) AS total_sales
FROM products p
INNER JOIN order_items oi ON p.product_id = oi.product_id
GROUP BY p.product_id, p.product_name
ORDER BY total_sales DESC
LIMIT 3;

### 3.2 多表关联的“避坑指南”

|问题|错误写法|正确写法|
|---|---|---|
|多表JOIN时忘记指定连接条件|`FROM a JOIN b`（产生笛卡尔积）|`FROM a JOIN b ON a.id = b.id`|
|左右表顺序搞反|用`RIGHT JOIN`但实际应`LEFT JOIN`|交换表顺序，用`LEFT JOIN`|
|多个JOIN条件混乱|在一个ON中塞多个条件，难以阅读|每个JOIN独立写ON条件；或多次JOIN（以保持可读性）|
|聚合时未考虑NULL|`SUM(amount)`在有NULL时仍可正常求和（NULL被忽略），但`COUNT(amount)`会跳过NULL|用`COALESCE`处理：`COALESCE(SUM(amount), 0)`|

## 四、常见误区

|误区|真相|
|---|---|
|“`JOIN`越多越好，一张大表全搞定”|❌ 过度JOIN会导致查询性能下降、数据冗余、维护困难。能在一张表中完成的查询不必拆成多表。数据库规范化与反规范化需要平衡|
|“`LEFT JOIN`和`INNER JOIN`的结果总是一样的”|❌ 当所有记录都能匹配时两者结果相同；当有记录无法匹配时，`LEFT JOIN`保留左表所有记录（右表为NULL），`INNER JOIN`会丢弃不匹配的记录|
|“子查询比`JOIN`慢，应该避免使用子查询”|❌ 某些子查询确实会降低性能（尤其是相关子查询在大数据量下）。但并非所有子查询都慢——`IN`子查询在某些数据库中会被优化器自动转换为`JOIN`。优先保证正确性，再考虑性能优化|
|“`UNION`和`UNION ALL`可以混用”|❌ `UNION`会去重，`UNION ALL`不去重。如果不需要去重，`UNION ALL`更快；如果需要去重但结果集无重复，两者结果相同但`UNION ALL`更高效|
|“外键约束一定会自动建索引，所以JOIN很快”|❌ 外键约束**不会自动创建索引**，但外键列通常需要建索引来提高JOIN性能。如果发现JOIN慢，检查外键列是否有索引（一般来说，外键列上建立索引是DB层面的最佳实践，但具体数据库的实现有所不同）|
|“自连接很少用，不用学”|❌ 自连接在处理层级数据（组织架构、商品分类、推荐链）时非常常见，是数据分析的必备技能|
