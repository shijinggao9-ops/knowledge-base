# Week 6 — Product Metrics & Analytics in SQL

> **Goal:** by Sunday you can take a raw `events` table for a real product, and — using nothing but SQL and pandas — name its North Star Metric, build a conversion funnel, compute retention cohorts, find the activation moment, and report DAU/WAU/MAU stickiness. No spreadsheet touches this data at any point.

Welcome to Week 6 of **C44 · Crunch Product**. Every week so far has been about *deciding* what to build: users, JTBD, problem framing, specs, prioritization. This week is about *proving it worked*. A PM who can only say "usage feels good" loses every argument to a PM who can say "activation is 34%, week-4 retention is 22%, and DAU/MAU stickiness dropped 6 points after the Feb 10 release — here's the query." That second PM is who this week builds.

We work against **Loopline**, the same fictional team task-management app from Week 1, except now you have its actual product event stream: 670 events from 168 visitors across an 8-week acquisition window, tracking everyone from their first landing-page view through repeat logins and completed tasks months later. One seed, one running example, every lecture/exercise/challenge/mini-project queries it — exactly like C33's single-table weeks, except this time the "single table" is the workhorse of every real analytics team: the events log.

**Data tooling rule for this week (and this course):** every question below is answered in **SQL** (PostgreSQL 16 primary, SQLite fallback) and, where noted, **Python + pandas**. Never a spreadsheet. Spreadsheets are Excel's job — that's [C41 · Crunch Excel](../../../C41-CRUNCH-EXCEL/), not this course. The moment you're managing, storing, or querying records — funnels, cohorts, retention — that's a job for a real query engine, because spreadsheets silently truncate rows, can't express a `LEFT JOIN`, and don't scale past a few thousand rows without corrupting a formula somewhere. You'll feel the difference this week: try to build an 8-week retention cohort table by hand in a grid, then try it in twelve lines of SQL.

## Learning objectives

By the end of this week, you will be able to:

- **Choose** a North Star Metric (NSM) for a product and decompose it into a metric tree of input metrics — while naming the vanity metrics and gameable metrics you deliberately did *not* pick.
- **Model** raw product events into a queryable `events` schema, and explain why "one wide events table" beats "one table per feature."
- **Build** a conversion funnel query in SQL using window functions (`MIN() OVER`, `ROW_NUMBER()`) to find each user's first occurrence of each funnel step.
- **Compute** weekly retention cohorts in SQL — the classic "cohort triangle" — and explain right-censoring (why recent cohorts look artificially weak).
- **Define and defend** an activation moment with evidence, not opinion — using a real retention-lift comparison.
- **Calculate** DAU, WAU, MAU, and the DAU/MAU stickiness ratio in SQL, and know which events belong in that calculation and which quietly wreck it.

## Set up the seed dataset (do this first)

Everything this week runs against two tables: `users` (everyone who finished signing up) and `events` (every tracked action, from anyone — including visitors who never signed up). Create them once.

**PostgreSQL:**

```bash
createdb loopline_events
psql loopline_events
```

**SQLite:**

```bash
sqlite3 loopline_events.db
```

Then run the schema:

```sql
CREATE TABLE users (
    user_id        INTEGER PRIMARY KEY,
    signup_date    DATE    NOT NULL,   -- date signup_completed happened
    plan           TEXT    NOT NULL,   -- 'free' or 'pro'
    country        TEXT,
    signup_channel TEXT                -- organic_search, paid_search, referral, social, direct
);

-- PostgreSQL: use SERIAL. SQLite: use INTEGER PRIMARY KEY AUTOINCREMENT.
-- Either way, event_id is generated for you — never include it in your INSERTs below.
CREATE TABLE events (
    event_id     SERIAL PRIMARY KEY,      -- SQLite: INTEGER PRIMARY KEY AUTOINCREMENT
    user_id      INTEGER   NOT NULL,      -- NOTE: not a foreign key to users — see below
    event_name   TEXT      NOT NULL,
    event_time   TIMESTAMP NOT NULL,
    session_id   INTEGER   NOT NULL
);
```

> **Why `events.user_id` has no foreign key to `users`.** `users` only holds people who *finished* signing up. `events` tracks everyone from the moment they hit the landing page — most of whom never sign up at all. That's not a bug; it's the whole point of a funnel. You'll see `user_id`s in `events` (e.g. `26`, `48`, `98`) that never appear in `users` — those are dropped-off visitors. If you `INNER JOIN events` to `users` without thinking about it, you silently throw away your entire top-of-funnel. Lecture 2 makes this mistake on purpose so you feel it once.
