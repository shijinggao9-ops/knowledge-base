### 题目 1：计算用户次日留存率

**题目**：
用户表 `users`（user_id, register_date）
登录表 `logins`（user_id, login_date）

计算 2026-07-01 注册的用户，次日（7月2日）留存率。

**答案**：
```sql
SELECT 
    COUNT(DISTINCT b.user_id) * 1.0 / COUNT(DISTINCT a.user_id) AS retention_rate
FROM users a
LEFT JOIN logins b 
    ON a.user_id = b.user_id 
    AND b.login_date = DATE_ADD(a.register_date, INTERVAL 1 DAY)
WHERE a.register_date = '2026-07-01';
```

**关键点：**
- 用 `LEFT JOIN` 而不是 `INNER JOIN`，否则没登录的用户会丢失
- `COUNT(DISTINCT)` 防止一个用户多次登录被重复计数
- `* 1.0` 把整数除法变成浮点数除法，否则结果是 0
- `DATE_ADD` 或 `DATE_SUB` 处理日期加减

### 题目 2：找出每个品类销售额 Top 3 的商品

**题目**：
订单表 `orders`（order_id, product_id, category, amount）

找出每个品类销售额最高的前 3 个商品。

**答案（窗口函数法）：**
```sql
WITH ranked AS (
    SELECT 
        product_id,
        category,
        SUM(amount) AS total_amount,
        RANK() OVER (PARTITION BY category ORDER BY SUM(amount) DESC) AS rk
    FROM orders
    GROUP BY product_id, category
)
SELECT * FROM ranked WHERE rk <= 3;
```

**关键点：**
- `RANK()` vs `ROW_NUMBER()` vs `DENSE_RANK()` 的区别：
  - `ROW_NUMBER()`：1,2,3,4（即使并列也强行排号）
  - `RANK()`：1,1,3,4（并列跳号）
  - `DENSE_RANK()`：1,1,2,3（并列不跳号）
- `PARTITION BY` 按品类分组，`ORDER BY` 组内排序
- 先聚合再排名，逻辑清晰

### 题目 3：计算各月份销售额的环比增长率和同比增长率

**题目**：
订单表 `orders`（order_id, order_date, amount）

计算每个月的销售额，以及环比增长率、同比增长率。

**答案：**
```sql
WITH monthly AS (
    SELECT 
        DATE_FORMAT(order_date, '%Y-%m') AS month,
        SUM(amount) AS total_amount
    FROM orders
    GROUP BY DATE_FORMAT(order_date, '%Y-%m')
),
with_lag AS (
    SELECT 
        month,
        total_amount,
        LAG(total_amount, 1) OVER (ORDER BY month) AS last_month,
        LAG(total_amount, 12) OVER (ORDER BY month) AS last_year
    FROM monthly
)
SELECT 
    month,
    total_amount,
    ROUND((total_amount - last_month) / last_month * 100, 2) AS mom_growth,
    ROUND((total_amount - last_year) / last_year * 100, 2) AS yoy_growth
FROM with_lag;
```

**关键点：**
- `LAG(column, n)` 取前 n 行的值，环比用 1，同比用 12
- 注意 `LAG` 在分组内的使用（如果需要按品类分组，加 `PARTITION BY category`）
- 处理除零错误：实际场景中需要加 `CASE WHEN last_month = 0 THEN NULL ELSE ... END`

### 题目 4：RFM 模型——给用户分群

**题目**：
订单表 `orders`（user_id, order_date, amount）

用 RFM 模型给用户分群：
- R（Recency）：最近一次消费距今天数
- F（Frequency）：消费次数
- M（Monetary）：消费总金额

**答案：**
```sql
WITH rfm AS (
    SELECT 
        user_id,
        DATEDIFF(CURRENT_DATE, MAX(order_date)) AS recency,
        COUNT(*) AS frequency,
        SUM(amount) AS monetary
    FROM orders
    GROUP BY user_id
),
rfm_score AS (
    SELECT 
        user_id,
        recency, frequency, monetary,
        NTILE(5) OVER (ORDER BY recency DESC) AS r_score,      -- 越近越好，所以DESC
        NTILE(5) OVER (ORDER BY frequency ASC) AS f_score,     -- 越多越好，所以ASC
        NTILE(5) OVER (ORDER BY monetary ASC) AS m_score       -- 越多越好，所以ASC
    FROM rfm
)
SELECT 
    user_id,
    recency, frequency, monetary,
    r_score, f_score, m_score,
    CASE 
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN '重要价值客户'
        WHEN r_score >= 4 AND f_score >= 4 THEN '重要保持客户'
        WHEN r_score >= 4 AND m_score >= 4 THEN '重要发展客户'
        WHEN f_score >= 4 AND m_score >= 4 THEN '重要挽留客户'
        ELSE '一般客户'
    END AS user_segment
FROM rfm_score;
```

**关键点：**
- `NTILE(n)` 把数据分成 n 等份，返回分位数（1-5）
- R 越小越好（消费越近越好），所以 `ORDER BY recency DESC`
- F/M 越大越好，所以 `ORDER BY frequency ASC`
- RFM 分群规则可以根据业务调整，上面的 CASE WHEN 只是示例

### 题目 5：漏斗分析——计算各环节转化率

**题目**：
用户行为表 `user_actions`（user_id, action, action_date）
行为包括：view（浏览）、click（点击）、add_cart（加购）、order（下单）

计算从浏览到下单的各环节转化率。

**答案：**
```sql
WITH funnel AS (
    SELECT 
        user_id,
        MAX(CASE WHEN action = 'view' THEN 1 ELSE 0 END) AS has_view,
        MAX(CASE WHEN action = 'click' THEN 1 ELSE 0 END) AS has_click,
        MAX(CASE WHEN action = 'add_cart' THEN 1 ELSE 0 END) AS has_cart,
        MAX(CASE WHEN action = 'order' THEN 1 ELSE 0 END) AS has_order
    FROM user_actions
    GROUP BY user_id
)
SELECT 
    SUM(has_view) AS view_count,
    SUM(has_click) AS click_count,
    SUM(has_cart) AS cart_count,
    SUM(has_order) AS order_count,
    ROUND(SUM(has_click) * 100.0 / SUM(has_view), 2) AS view_to_click,
    ROUND(SUM(has_cart) * 100.0 / SUM(has_click), 2) AS click_to_cart,
    ROUND(SUM(has_order) * 100.0 / SUM(has_cart), 2) AS cart_to_order,
    ROUND(SUM(has_order) * 100.0 / SUM(has_view), 2) AS overall_conversion
FROM funnel;
```

**关键点：**
- 用 `MAX(CASE WHEN ...)` 把长表变宽表（行转列）
- 漏斗分析的核心是「去重后的用户数」，不是行为次数
- 转化率 = 下一环节人数 / 上一环节人数

### 题目 6：找出连续登录 3 天以上的用户

**题目**：
登录表 `logins`（user_id, login_date）

找出连续登录 3 天及以上的用户。

**答案：**
```sql
WITH distinct_logins AS (
    SELECT DISTINCT user_id, login_date FROM logins
),
with_grp AS (
    SELECT 
        user_id,
        login_date,
        DATE_SUB(login_date, INTERVAL 
            ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) DAY
        ) AS grp
    FROM distinct_logins
),
streaks AS (
    SELECT 
        user_id, grp, COUNT(*) AS streak_length
    FROM with_grp
    GROUP BY user_id, grp
)
SELECT DISTINCT user_id FROM streaks WHERE streak_length >= 3;
```

**关键点：**
- 经典「连续问题」解法：用日期减去排序序号，如果连续则差值相同
- 先去重（`DISTINCT`），防止一天多次登录干扰
- `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date)` 给每个用户的登录日期排序

### 题目 7：计算 7 日移动平均销售额

**题目**：
订单表 `orders`（order_date, amount）

计算每天的销售额及过去 7 天（含当天）的移动平均。

**答案：**
```sql
SELECT 
    order_date,
    SUM(amount) AS daily_amount,
    AVG(SUM(amount)) OVER (
        ORDER BY order_date 
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS moving_avg_7d
FROM orders
GROUP BY order_date
ORDER BY order_date;
```

**关键点：**
- `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` 取当前行及前 6 行，共 7 天
- 也可以用 `RANGE BETWEEN INTERVAL '6' DAY PRECEDING AND CURRENT ROW`（MySQL 8.0+）
- 移动平均用于平滑波动，看出趋势

### 题目 8：查找重复数据 / 去重保留最新记录

**题目**：
用户表 `users`（user_id, name, update_time）

同一个 user_id 可能有多条记录，保留 update_time 最新的那条。

**答案（窗口函数法）：**
```sql
WITH ranked AS (
    SELECT *,
        ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY update_time DESC) AS rn
    FROM users
)
SELECT * FROM ranked WHERE rn = 1;
```

**答案（子查询法）：**
```sql
SELECT * FROM users u1
WHERE update_time = (
    SELECT MAX(update_time) FROM users u2 WHERE u2.user_id = u1.user_id
);
```

**关键点：**
- 窗口函数法更简洁，性能通常更好
- 子查询法更直观，适合简单场景
- 如果要求保留所有并列最新的，用 `RANK()` 代替 `ROW_NUMBER()`

### 题目 9：多表关联——找出有订单但没有评价的用户

**题目**：
用户表 `users`（user_id, name）
订单表 `orders`（order_id, user_id）
评价表 `reviews`（review_id, order_id）

找出下过单但没有留下评价的用户。

**答案：**
```sql
SELECT DISTINCT u.user_id, u.name
FROM users u
JOIN orders o ON u.user_id = o.user_id
LEFT JOIN reviews r ON o.order_id = r.order_id
WHERE r.review_id IS NULL;
```

**关键点：**
- `JOIN orders` 确保用户下过单
- `LEFT JOIN reviews` 保留没有评价的订单
- `WHERE r.review_id IS NULL` 筛选出没有评价的记录
- 注意 `DISTINCT`，防止一个用户多笔订单被重复计数

### 题目 10：行列转换——把长表变宽表

**题目**：
销售表 `sales`（month, product, amount）

把数据转成：每行是一个产品，每列是一个月的销售额。

**答案：**
```sql
SELECT 
    product,
    SUM(CASE WHEN month = '2026-01' THEN amount ELSE 0 END) AS Jan,
    SUM(CASE WHEN month = '2026-02' THEN amount ELSE 0 END) AS Feb,
    SUM(CASE WHEN month = '2026-03' THEN amount ELSE 0 END) AS Mar
FROM sales
GROUP BY product;
```

**关键点：**
- `CASE WHEN` + `SUM` 是行列转换的经典组合 
- 如果月份很多，可以用动态 SQL（但面试手写通常不要求）

## 三、业务分析思维——指标拆解框架

### 3.1 万能拆解公式：某指标下降了 X%，怎么分析？

**面试高频题**："某电商 APP 日活下降了 10%，你怎么分析？"

**回答框架（结构化、有层次）：**

```
第一步：确认问题
  → 是突然下降还是趋势性下降？
  → 是整体下降还是某类用户/某地区/某版本下降？
  → 数据本身有没有问题？（埋点故障？统计口径变了？）

第二步：拆解维度
  用户维度：新用户/老用户、iOS/Android、不同城市层级
  渠道维度：自然流量/付费流量/社交裂变/搜索
  产品维度：不同版本（是否新版有bug？）、不同功能模块
  时间维度：是否节假日？是否竞品有大促？

第三步：定位原因
  → 如果是某渠道下降：该渠道投放是否减少？成本是否上升？
  → 如果是某版本下降：是否有bug？用户体验是否变差？
  → 如果是某地区下降：是否有政策变化？网络问题？
  → 如果是竞品影响：竞品最近有什么动作？

第四步：给出建议
  → 短期：修复bug、加大投放、召回活动
  → 长期：优化产品体验、调整渠道策略、提升留存
```

**面试话术：**
"如果日活下降10%，我不会直接给结论，而是按四个步骤分析：

第一，**确认问题真实性**——先排除数据问题，比如埋点故障、统计口径变化；

第二，**多维度拆解**——按用户（新老）、渠道（自然/付费/社交）、版本（iOS/Android）、地域等维度看，是哪个维度在掉；

第三，**定位根因**——如果发现是付费渠道掉了一半，进一步看是预算减少了还是转化效率下降了；

第四，**给出 actionable 的建议**——短期做什么止血，长期做什么根治。

我在贝恩杯做案例分析时，用的就是这种'先拆解再归因'的思维。"

### 3.2 指标体系设计

**AARRR 模型（用户生命周期）：**

| 阶段 | 指标 | 计算方式 | 优化方向 |
|------|------|---------|---------|
| 获客 Acquisition | 新增用户数、CAC | 总获客成本/新增用户数 | 渠道优化、裂变活动 |
| 激活 Activation | 首次完成核心行为率 | 完成核心行为的用户/总注册用户 | 新手引导、首单优惠 |
| 留存 Retention | 次日/7日/30日留存率 | N天后仍活跃的用户/当天新增用户 | 推送、会员体系 |
| 变现 Revenue | ARPU、LTV、GMV | 总收入/用户数 | 定价策略、交叉销售 |
| 推荐 Referral | 分享率、K因子 | 每个用户带来的新用户数 | 邀请奖励、社交裂变 |

**面试话术：**
"AARRR 是分析用户生命周期的经典框架。我在挑战杯做用户增长时，就是从这五个环节设计的：获客端用裂变活动拉新，激活端用首单优惠促转化，留存端用积分体系提粘性。这个框架可以迁移到任何用户型产品的数据分析中。"

## 四、AB 测试

### 4.1 AB 测试设计步骤

| 步骤 | 内容 | 关键点 |
|------|------|--------|
| 1. 确定目标 | 要优化什么指标？ | 只能有一个核心指标（North Star Metric） |
| 2. 提出假设 | 改动A会比改动B更好，因为... | 假设要可验证、可量化 |
| 3. 设计实验 | 实验组/对照组、样本量、实验时长 | 随机分组，确保两组基线一致 |
| 4. 确定样本量 | 用统计功效（Power）和显著性水平计算 | 通常 α=0.05，Power=0.8 |
| 5. 运行实验 | 确保实验期间无其他干扰因素 | 避开节假日、大促、版本更新 |
| 6. 分析结果 | 统计显著性 + 业务显著性 | p<0.05 不代表值得上线 |
| 7. 决策上线 | 显著且正向 → 全量；不显著 → 保留原方案；负向 → 回滚 | 记录实验结论，沉淀知识 |

### 4.2 常见面试问题

**Q：AB 测试结果 p<0.05，但业务方觉得提升太小不想上线，怎么办？**

**回答：**
"统计显著性（p<0.05）只说明'结果不是偶然'，但不说明'结果值得做'。这时候需要看**业务显著性**——提升的幅度是否足以覆盖开发成本、运营成本。如果提升只有0.1%，但全量后每年能多赚100万，那就值得做；如果提升0.1%但每年只多赚1万，那就不值得。

另外，还要看**置信区间**。如果95%置信区间是[0.05%, 0.15%]，说明真实提升大概率在这个范围内，业务方可以据此决策。"

**Q：实验组和对照组的样本量怎么确定？**

**回答：**
"样本量取决于四个因素：
1. 基准转化率（对照组的当前水平）
2. 期望提升的最小幅度（MDE，Minimum Detectable Effect）
3. 显著性水平 α（通常0.05）
4. 统计功效 1-β（通常0.8）

可以用在线样本量计算器（如Evan Miller的Sample Size Calculator）输入这四个参数得到结果。核心逻辑是：期望检测的提升越小，需要的样本量越大。"

### 5.2 数据透视表要点

**面试可能问：**
- "你用过数据透视表吗？举一个实际例子"
- "透视表和函数求和有什么区别？"

## 六、统计学基础

### 6.1 核心概念

| 概念 | 定义 | 面试场景 |
|------|------|---------|
| 均值 vs 中位数 | 均值受极端值影响，中位数更稳健 | 收入分析用中位数 |
| 标准差 | 数据离散程度 | 用户消费金额的波动 |
| 百分位数 | P50/P90/P99 | 用户分层、性能分析 |
| 相关系数 | -1到1，衡量线性相关 | 相关≠因果！ |
| p-value | 原假设成立的概率 | p<0.05拒绝原假设 |
| 置信区间 | 真实值大概率落在的区间 | AB测试结果解读 |
| 第一类错误 | 假阳性（以为有效实际无效） | α=0.05就是控制第一类错误 |
| 第二类错误 | 假阴性（以为无效实际有效） | Power=0.8就是控制第二类错误 |

### 6.2 相关≠因果

**面试高频陷阱题：**
"冰淇淋销量和溺水死亡人数高度正相关，说明吃冰淇淋导致溺水吗？"

**回答：**
"不说明。相关不等于因果。这两个变量的共同原因是'气温'——夏天热，吃冰淇淋的人多，游泳的人也多，溺水风险上升。在数据分析中，我们必须警惕'伪相关'，要通过实验设计（如AB测试）或因果推断方法（如双重差分）来验证因果关系。"
